What the modes actually do

The engine stages reads and writes, then validates them at commit. The difference is what gets validated.

none

No validation. Reads and writes race. Use it only as a benchmark baseline.

Lost updates and overselling are expected.

optimistic

Snapshot reads, then validate every read and write base version at commit.

Default. Serializes the tracked key set and rejects write skew.

snapshot

MVCC reads with first-committer-wins on the write set only.

No lost updates, but write skew remains possible.

serializable

Optimistic validation plus a serialization-graph audit for cycle diagnostics.

Highest assurance; conflict detection can be stricter.

pessimistic

Strict two-phase locking: reads take locks and hold them until commit.

Predictable under hot keys; waits instead of retrying.

Why reads matter

Write skew happens when each transaction writes a different key but reads the other's key to make its decision. Validating only the write set cannot see it. Validating the read set can.

Why retries are safe

A conflict means the transaction did not commit. The whole body re-runs on a fresh snapshot. An unknown failure is never silently retried.

Why this is hard

Framework checkpointers persist messages, not conflict detection across concurrent tool calls. That coordination layer is what StatePact provides.
